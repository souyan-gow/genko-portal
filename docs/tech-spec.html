2. 画面を作る技術

React（リアクト）

役割画面を「部品」に分けて作り、本文やカーソルが変わったら、必要な部分だけを描き直す
使いどころすべての画面。原稿用紙のページ・マス、記号入力バー、上部バーなど
選んだ理由利用者が非常に多く、情報が豊富で、AI でも扱いやすい。「中身が変わらない部品は描き直さない」という仕組みがあり、何百ものマスを持つ原稿用紙を速く描ける
ほかの候補Vue、Svelte。どちらでも作れるが、利用者の多さと情報量で React を選んだ

TypeScript（タイプスクリプト）

役割プログラムの中の値に「種類（型）」を付け、書き間違いを動かす前に見つける
使いどころすべてのプログラム
選んだ理由原稿用紙の割り付けでは「本文の何文字目」「何行目」「何マス目」など、数字の意味の取り違えが起きやすい。型があると、そうした間違いを早く見つけられる
ほかの候補JavaScript（型のない言葉）。手軽だが、間違いに気づきにくい

Vite（ヴィート）

役割開発中に手元でアプリを動かす。公開用に、プログラムを小さくまとめたファイルを作る
使いどころ開発と公開の準備
選んだ理由起動と更新がとても速く、設定が少ない。Vercel が標準で対応している
ほかの候補Next.js（サーバーの処理も書ける仕組み）。GENKO はサーバーの処理を Firebase に任せるので、そこまでは要らない

3. 縦書き・ルビを表す技術

技術使いどころ選んだ理由
CSS の writing-mode: vertical-rl 原稿用紙の各マスの文字 句読点が右上に寄る、括弧や「ー」が縦向きになる、といった縦書きの文字の形を、ブラウザが正しく出してくれる。自分で文字を回転させると、記号ごとに調整が必要になる
自前のマス目の配置 原稿用紙のマスと行、ページ ブラウザに任せると、禁則やルビの位置が原稿用紙の決まりと合わない。マスの位置は GENKO が計算し、文字の形だけをブラウザに任せる
CSS の text-combine-upright 2桁の数字の縦中横 1マスに数字を横並びで入れる、ブラウザに備わった機能
CSS の text-emphasis 傍点 縦書きなら右、横書きなら上に、自動で点を付けてくれる
HTML の ruby 要素 横書きの読む表示のルビ ルビを付けるための HTML の標準の書き方。原稿用紙ではルビをマスの外（行の間）に置く必要があるため、こちらは自前で配置している
透明な入力欄 PC の原稿用紙での日本語入力 日本語入力（変換）は、ブラウザの入力欄でしか正しく受け取れない。入力欄の文字を透明にしてカーソルのマスに重ね、受け取った文字をマス目に描く

「マス目に直接入力できるか」は、作り始める前のフェーズ0で、試作して確かめました。変換中の文字がマス目上で崩れないことを確認してから、この方式に決めています。

4. ログインと保存の技術

Firebase Authentication（ファイアベース オーセンティケーション）

役割Google アカウントでのログインを受け持つ
使いどころログイン画面。ログイン中の人が持ち主かどうかの判定
選んだ理由パスワードを GENKO で預からずに済み、Google アカウントの安全性（2段階認証など）をそのまま使える。保存に使う Firestore と組み合わせて、持ち主だけに読み書きを許す規則を作れる
やり方の工夫ログインは小さな画面（ポップアップ）を開く方式。画面を切り替える方式は、iPhone の Safari のプライバシー保護の機能で失敗することがあるため

Cloud Firestore（クラウド ファイアストア）

役割作品・章・設定を保存するデータベース
使いどころ自動保存、作品・章の一覧、設定、ほかの端末での変更の受け取り
選んだ理由 ・変更をすぐに知らせてくれる：ほかの端末で書いた内容が、再読み込みしなくても届く
・端末の中に写しを持てる：書いた内容を先に端末に保存し、通信が切れても消えない
・自分でサーバーを用意しなくてよい：管理の手間がない
・無料の範囲が広い：個人の執筆なら無料で収まる
やり方の工夫端末の中の写し（persistentLocalCache）を有効にし、PC で複数のタブを開いても壊れない設定にしている
ほかの候補Supabase など。同期とオフラインの扱いのしやすさで Firestore を選んだ

5. 配る・管理する・確かめる技術

技術役割選んだ理由
Vercel（ヴァーセル）アプリを公開して配るGitHub にプログラムを置くと、自動で公開し直してくれる。個人の利用なら無料。Vite に標準で対応している
GitHub（ギットハブ）プログラムの置き場所と変更の履歴いつ何を変えたかが残り、前の状態に戻すこともできる。Vercel とつながる
Vitest（ヴィテスト）自動テストを動かすVite と同じ設定で動き、速い。原稿用紙のルールが壊れていないかを、変更のたびに確かめられる

このドキュメントのサイトは、アプリとは別の GitHub のリポジトリに置き、GitHub Pages で公開しています。アプリが止まっても、こちらは見られます。

6. あえて使っていないもの

使う部品が少ないほど、壊れにくく、直しやすくなります。次のものは、あえて使わず自前で作っています。

よく使われるもの使わない理由
文章エディタの部品（ProseMirror など）横書きの文書向けに作られていて、縦書きのマス目への直接入力や原稿用紙の割り付けには合わない
画面切り替えの部品（React Router など）画面が5つだけなので、アドレスの「#」以降で切り替える小さな仕組みで足りる
ルビ・記法を読み取る部品カクヨム式の記法は決まりが少なく、自前で作ったほうが原稿用紙の割り付けと組み合わせやすい
見た目の部品集色とフォントを細かく決めたいので、自分で書いた見た目（CSS）だけで作っている

7. 動作環境と制約

項目内容
確かめている端末iPhone 14（Safari）、PC（Chrome）
画面の幅360px 以上
iPhone のブラウザSafari のみ。Google アプリや iPhone 版 Chrome では、ブラウザの制限（サイトをまたいだ情報の受け渡しの制限）でログインできない。必要になれば、ログインを公開先と同じアドレスで行う方式に変えて対応できる
スマホの原稿用紙モード表示のみ。スマホでマス目に直接入力すると、キーボードと画面の取り合いで操作が難しいため、横書きで書く方式にしている
1章の長さ保存の上限は約30万字。25万字を超えたら章を分けるよう表示する
置けるファイル文字（テキスト）だけ。画像や PDF を置くには別の保存場所（Cloud Storage）が必要で、料金プランの変更が要る

8. プログラムの構成

genko/
├── docs/                 仕様のドキュメント
├── firestore.rules       データのアクセス規則
├── src/
│   ├── pages/            画面（ログイン、作品一覧、章一覧、執筆、設定）
│   ├── components/       画面の部品（記号入力バー、モード切替、章一覧など）
│   ├── editor/
│   │   ├── layout/       原稿用紙の割り付けとカーソル（画面に依存しない処理）
│   │   ├── genko/        原稿用紙モード
│   │   └── yoko/         横書きモード
│   ├── notation/         ルビ・傍点の記法の読み取り
│   ├── firebase/         ログイン、データの読み書き、自動保存
│   ├── io/               .txt の読み書き、バックアップ
│   └── styles/           色（ライト・ダーク）と共通の見た目
└── tests/                自動テスト
  • 原稿用紙の割り付け（editor/layout）は、画面とは切り離した処理にしている。そのため、自動テストで正しさを確かめられる
  • 色はすべて一か所（styles）で管理し、ライトとダークの両方を決めている
  • Firebase の設定値は、プログラムの置き場所（GitHub）には入れず、手元と Vercel にだけ登録している。なお、Firebase の Web 用の設定値はもともと秘密の値ではなく、データはアクセス規則で守っている

9. テストの方針

確かめ方対象
自動テスト（119件）原稿用紙の割り付け（禁則、記号のマス数、ルビ、字下げ、ページ跨ぎ、枚数・文字数の数え方）、記法の読み取り、カーソルと削除、記号入力バー、元に戻す、設定の2段階、.txt の読み書き、バックアップの形式
持ち主が実機で確認見た目と操作感、日本語入力、スマホのキーボードまわり、ログイン、保存と同期

原稿用紙のルール（docs/genko-rules.md）に書かれた例は、すべてそのまま自動テストにしています。

Firebase（Authentication・Firestore）無料プラン（Spark）0円使う人が1人で、データは文字だけ。保存は入力が止まったときだけ行うので、書き込みの回数も少ない
